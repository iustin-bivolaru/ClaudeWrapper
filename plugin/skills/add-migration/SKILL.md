# Add an Alembic migration

First find how the project runs Alembic: a Makefile target, `PYTHONPATH=.`, `uv run` or `poetry run`, and where the DB URL comes from (`.env`, an env var). Run every command from the repo root in that way.

If the DB URL comes from `.env`, the sandbox blocks it. Write the migration file, then ask the user to run the `alembic` commands (`! make migrate` or similar) and paste the output. Never read `.env` to find the URL.

## Steps

1. Make sure the ORM change is in place and the model is imported wherever `alembic/env.py` loads the metadata from.
2. Check there is a single head: `alembic heads`. If there are two, tell the user before going on. They may want `alembic merge`.
3. Generate: `alembic revision --autogenerate -m "short imperative description"`. This needs the dev database running. Without one, use `alembic revision -m ...` and write the operations by hand.
4. **Review the generated file. Autogenerate misses or gets wrong:**
   - **Enum value changes.** Adding a value to a Python enum backing a Postgres enum generates nothing. Write `op.execute("ALTER TYPE <type> ADD VALUE '<V>'")` yourself, and use `RENAME VALUE` for renames. Postgres can't drop enum values, so say in the downgrade docstring that it is a no-op.
   - **New enum types.** `sa.Enum(..., name=...)` must match the name in the ORM.
   - **Triggers, functions, schemas, grants, extensions.** These are never autogenerated. Write them with `op.execute`, and drop them in the downgrade.
   - **Column renames** show up as drop + add, which loses data. Change them to `op.alter_column(..., new_column_name=...)`.
   - **New NOT NULL columns** on a table that has rows need a `server_default` or a backfill step.
5. Give `upgrade()` and `downgrade()` one-line docstrings. Keep `revision` and `down_revision` as generated.
6. Apply and round-trip: `alembic upgrade head`, then `alembic downgrade -1`, then `alembic upgrade head`.
7. If the change needs manual work after deploy (reindexing, re-running a job), write it down where the project keeps operational notes (README, docs).

## Rules
- Never edit a migration that is already committed. It may have run on someone's database. Write a new revision.
- Don't import application code (services, settings) into migrations. Write any values they need inline, so old migrations keep working as the app changes.
- For a risky migration, ask a migration review subagent if the project has one, or the user.
